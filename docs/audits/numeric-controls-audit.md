# Numeric Controls Audit

Updated: 2026-03-26 16:17 EDT  
Status: Audit and classification complete. No implementation changes in this pass.

## Scope

- Included: audio-facing numeric controls in `web/src` that affect DSP, plugin parameters, automation, routing, MIDI mapping, device calibration, or operator tuning.
- Excluded from the refactor scope for now: non-audio admin/search/server forms in `web/src/app/components/HostMachine/*`, `web/src/app/components/ShoppingSearchDialog.tsx`, `web/src/app/components/OnboardingWizard.tsx`, and `web/src/map2/components/WWWPanel.tsx`.
- Method:
  - AST sweep for `ParameterKnob`, `NumberInput`, `NumericInput`, raw `input[type=range|number]`.
  - Manual pass for the custom `MPX1Knob` path and the MPX-1 panel placeholders.
  - Focused reads of the main control families and the highest-volume surfaces (`PassionFXCard`, `DrumsPage`, MPX1, IntelFX, Tesira, JUCE Grid, LV2 editor).

## Executive Summary

- First-pass scan found 296 numeric widget entry points in `web/src`.
- After excluding 8 non-audio admin/search/server widgets, 288 AST-matched audio-facing numeric controls remain in scope.
- A manual follow-up found 3 additional `MPX1Knob` custom knob entry points, bringing the effective in-scope audit total to 291 control entry points.
- Distribution of in-scope control families:
  - `ParameterKnob`: 146
  - `NumberInput`: 101
  - Raw `input[type=range]`: 28
  - Raw `input[type=number]`: 10
  - `MPX1Knob`: 3
  - Active `ParameterSlider` usage: 0
- Only 7 call sites currently provide any `onChangeEnd`/commit callback. Most controls are effectively live-only at the call-site level.
- `ParameterKnob` exposes `isLogarithmic`, but the shared implementation ignores it today, so intended log controls still move through the linear `NumericInput` path.
- `NumericInput` already provides text entry, arrow keys, Home/End, Enter/Escape, double-click reset, wheel, and touch/pen drag, but it does not provide true live-vs-commit separation and does not support mouse drag.
- Tesira is internally inconsistent:
  - `TesiraEQTab` is live-on-change directly to the API.
  - `TesiraLevelsTab`, `TesiraMixerTab`, and `TesiraDspBlockPanel` stage draft values and require explicit apply buttons.
- `DrumsPage` is the largest raw-input hotspot with 34 numeric controls spread across transport, mixer, per-pad synth/filter/CV, step locks, and MIDI mapping.

## Current Control Families

- `NumericInput` in `web/src/app/components/NumericInput/NumericInput.tsx`
  - Type: text field with `role="slider"`.
  - Interaction: keyboard arrows, Home/End, Enter/Escape, wheel, double-click reset, touch/pen drag.
  - Missing for the target state: mouse drag, real log scaling, separate live and commit channels, controlled wheel-commit semantics.
  - Current commit issue: `onChangeEnd` fires for wheel and arrow interactions immediately, so it is not a reliable “commit only” signal.
- `NumberInput` in both `web/src/app/components/Controls/NumberInput.tsx` and `web/src/map2/components/NumberInput.tsx`
  - Thin wrapper over `NumericInput`.
  - Most call sites only use `onChange`, so they do not currently separate live and commit semantics.
- `ParameterKnob` in `web/src/app/components/Controls/ParameterKnob.tsx`
  - Also just a `NumericInput` wrapper.
  - Intended knob/log behavior exists in API shape but not in actual motion math.
- `ParameterSlider` in `web/src/app/components/Controls/ParameterSlider.tsx`
  - Not a real slider. It is only a backwards-compatibility alias to `NumberInput`.
  - There are no active uses of the alias in the current codebase.
- `MPX1Knob` in `web/src/app/components/MPX1/MPX1Knob.tsx`
  - Real custom knob with mouse drag, shift-fine adjustment, canvas rendering, and double-click prompt entry.
  - Missing keyboard handling, explicit commit channel, and shared formatting/scaling behavior.
- Raw native inputs
  - Still used heavily in `DrumsPage` and Tesira surfaces.
  - These have browser-default keyboard behavior only, no reset behavior, and no shared live/commit contract.

## Key Findings

- The project already has one promising primitive (`NumericInput`), but it is not yet the professional-grade real-time control layer described in the brief.
- Three control stacks now coexist:
  - shared `NumericInput` wrappers,
  - bespoke `MPX1Knob`,
  - raw HTML number/range controls.
- Logarithmic intent is already present in many call sites, especially plugin cards and runtime registries, but the shared control runtime does not honor it.
- Several operator surfaces use live API mutation on every change:
  - most plugin cards,
  - `DrumsPage`,
  - `TesiraEQTab`,
  - IntelFX and MPX1 runtime parameter panels.
- Several engineering/calibration surfaces intentionally stage drafts before apply:
  - Tesira Levels,
  - Tesira Mixer,
  - Tesira DSP block editor.
- A few legacy blend controls already show why explicit commit semantics matter:
  - `ABQuickToggle` calls both change and commit paths inside the same `onChange` handler.

## Classification Summary

- `CONTINUOUS_LINEAR`
  - The dominant class.
  - Includes mix, blend, volume, gain, pan, send, threshold, makeup, modulation depth, diffusion, duck amount, brightness, alert volume, and most range sliders in `DrumsPage`.
- `CONTINUOUS_LOG`
  - Present anywhere the parameter is inherently frequency- or time-shaped.
  - Includes EQ frequency, delay time, low/high cut, modulation rate, attack, release, decay, crossover, resonance/Q, and other frequency/time parameters in plugin cards and runtime registries.
  - Important caveat: many of these are only intended-log today; actual knob motion is still linear.
- `STEPPED_NUMERIC`
  - Includes BPM, pattern, variation, stages, voices, CC number, MIDI channel, parameter index, target index, program numbers, slot numbers, crossfade sizes, and semitone pedal ranges.
- `CALIBRATION / ENGINEERING`
  - Includes buffer size, MIDI deadzone low/high, expression output min/max, Tesira trims and matrix gains, LCD brightness and timing, Edirol headphone volume, and MIDI export timing values.
- `ENUM_DISGUISED_AS_NUMERIC`
  - Present in the runtime registries for MPX1 and IntelFX, but the current UI already routes those parameters to `<select>` rather than numeric entry.
  - Result: there are effectively no in-scope numeric widgets that should stay numeric while representing enums.

## Highest-Risk Gaps To Carry Into Implementation

- Real logarithmic motion is missing even where the current code advertises `isLogarithmic` or `log_taper`.
- Mouse drag is inconsistent:
  - `NumericInput` supports touch/pen drag only.
  - `MPX1Knob` supports mouse drag.
  - raw sliders support native browser drag.
- Commit semantics are inconsistent:
  - most wrappers are live-only,
  - some dialogs are draft/apply,
  - `JuceGridParameterEditor` partially separates change and end,
  - `ABQuickToggle` merges change and commit into one handler.
- Reset/default behavior is inconsistent:
  - wrapper-based controls have double-click reset,
  - `MPX1Knob` uses prompt entry instead,
  - raw range/number inputs usually have no reset path.
- Accessibility is inconsistent:
  - wrapper-based controls expose slider semantics,
  - raw inputs rely on default browser behavior,
  - `MPX1Knob` lacks keyboard support.

## Audit Conclusion

- The codebase already has enough shared infrastructure to avoid a greenfield rewrite, but not enough behavioral consistency to migrate incrementally without a written standard.
- The first implementation pass should refactor around the existing `NumericInput` foundation, replace raw parameter sliders in the chosen pilot surfaces, and retire `MPX1Knob` behavior into the shared model instead of preserving a separate control stack.
