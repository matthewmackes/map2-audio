Purpose
Create one ultra-high-resolution, technically accurate, poster-grade infographic that explains MAP2 as a layered platform, not as a single app. The image must show service relationships, workflows, signal paths, authority layers, operator surfaces, node roles, cluster/network relationships, hardware integrations, and real use cases.

This image is not a marketing fantasy piece. It is a dense technical infographic for engineers, operators, contributors, and advanced musicians. Accuracy is more important than visual drama.

Non-Negotiable Accuracy Rules
1. Present MAP2 as an open-source educational and research platform with serious implementation depth, not as a universally production-ready commercial appliance.
2. Do not claim "measured sub-3 ms latency." The accurate framing is:
   - 64-sample theoretical floor at 48 kHz = 2.67 ms per buffer
   - measured realistic latency on the current audit host is about 4-7 ms
3. Show that live truth is not inferred from the editor or cached UI state.
   - The node-local realtime runtime is the only authority for whether a snapshot is actually live.
   - Backend and UI may show requested, pending, warning, offline, or failed, but must not fake live confirmation.
4. Show the current configuration authority model exactly:
   - /etc/map2 = host desired configuration
   - /var/lib/map2 = durable service and cluster state
   - ~/.map2 = user, operator, and session-scoped state
   - runtime/external systems such as PipeWire, /proc, etcd, and Raft = observed or control-plane state, not static config
5. Show that authoritative audio state uses etcd by default, under the namespace /map2/audio-state/v1, with desired, committed, and observed layers.
6. Show that snapshot persistence authority is the graph-document model:
   - snapshots.document
   - snapshot_revisions.document
   - state_authority_assets
   Legacy snapshot_* tables are compatibility projections, not the future source of truth.
7. Show the three primary deployment modes:
   - Audio
   - All-in-One
   - Management
   Do not elevate "frontend-only" as a primary mode. It appears in some backend deployment APIs, but the shipped mode-switching workflow is built around the three primary modes above.
8. Show the supported web/backend/observability port contract:
   - 3000 = production web UI
   - 8080 = FastAPI backend and WebSocket services
   - 9090 = Prometheus on management or all-in-one nodes only
   - 3001 = Grafana on management or all-in-one nodes only
   - optional port 80 proxy exists only as legacy compatibility
9. Show that audio nodes export lightweight metrics only. They do not host local Prometheus or Grafana by default.
10. Do not invent a Kubernetes layer, message bus, cloud SaaS backend, or proprietary orchestration stack. Keep everything grounded in the repo.
11. Do not draw every subsystem as equally mature. Use visible maturity badges where the repo provides them.
12. If space becomes tight, compress route-level details, but do not remove any of the 25 required concept blocks below.

Required Cross-Cutting Workflows
In addition to the 25 blocks, draw the following named workflows across the poster as highlighted path overlays. These should cross multiple lanes and be labeled.

Workflow A. Provision a Host
Installer -> host config -> packages -> systemd units -> mode policy -> verify

Workflow B. Launch Local Services
boot manager -> backend -> orchestrator -> local services -> web UI -> optional LCD

Workflow C. Author and Publish a Snapshot
JUCE-GRID or snapshot editor -> snapshot draft -> compiled intent -> authoritative desired state -> committed state -> runtime apply -> runtime live confirmation -> WebSocket/UI update

Workflow D. Local Audio Signal Path
physical input or audio interface -> PipeWire/JACK -> JUCE engine graph -> plugin chain -> output paths -> local outputs and/or AVB talkers

Workflow E. Multi-Node Audio Path
local node -> AVB talker/listener matrix -> PTP-synced network -> remote node -> remote path confirmation

Workflow F. Controller-Driven Performance
physical surface or MIDI controller -> MIDI Hub or surface runtime -> backend route/service -> snapshot/brain/engine action -> runtime state update -> surface feedback and UI update

Workflow G. Cluster Adoption
discover remote candidate -> readiness/trust -> claim/adopt -> optional clone profile -> optional AVB auto-provision -> visibility/heartbeat integration

Workflow H. Observability
backend exporter on each node -> Prometheus on management/all-in-one -> Grafana dashboards -> operator view

Explicit Mistakes to Avoid
1. Do not turn the image into a generic cloud microservices diagram.
2. Do not draw Kubernetes, Docker, or browser-only SaaS architecture.
3. Do not present the web UI as the system brain. The backend and runtime are the system brain.
4. Do not present the backend database as the live truth for snapshot activation.
5. Do not omit PipeWire.
6. Do not omit etcd.
7. Do not omit cluster/adoption/visibility just because they are less glamorous than DSP.
8. Do not omit the operator layers. MAP2 includes web UI, TUIs, touchscreen clone, and LCD.
9. Do not omit hardware ecosystems. MAP2 is not only a software editor.
10. Do not depict all features as equally stable.
11. Do not use bright rainbow colors everywhere. Use a controlled technical palette.
12. Do not use decorative gradients as the main design language.
13. Do not use tiny unreadable labels. Fewer words per label is acceptable, but the key labels must remain legible.
14. Do not draw musical instruments as the main subject. The main subject is the platform architecture.
15. Do not claim that MAP2 is a full DAW replacement in the image.
